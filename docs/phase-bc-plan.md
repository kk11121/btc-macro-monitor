## 3. ジョブと発表待ち受け

| ジョブ | mode | 起動 | 中身 |
|---|---|---|---|
| 朝のまとめ | `morning` | 今と同じ（cron-job.org 7:47、予備は定時実行） | 予定と予想値の更新、利下げ確率、日次フロー（今と同じ）、全指標、稼働状況（SoSoValue の残り回数）。1日は月次レポートも |
| 毎時の監視 | `hourly` | 今と同じ（cron-job.org 毎時23分、予備は定時実行） | VIX、利下げ確率の変化、FOMC（臨時を含む）、日次フロー、経済指標の予備確認、**発表待ち受け**、BTC 価格の書き足し |
| 月次レポート（手動） | `monthly` | 手動だけ | 朝のまとめが送れなかったときの送り直し用 |

**cron-job.org の予定は増やさない。** 今ある朝と毎時の2つのまま。

### 毎時の監視の中の発表待ち受け

順番：

1. いつもの確認（VIX、FOMC、日次フロー、利下げ確率、経済指標の予備確認）を先に済ませる。待っている間に VIX などが遅れないようにするため
2. 当日の発表で、まだ取れていないものを探す。対象は、時刻がこれから60分以内のものと、時刻から45分以内のもの（予備の定時実行が遅れて動いたときに拾うため）
3. あれば、発表の数分前に予想値を取り直し（SoSoValue と ForexFactory）、発表時刻まで待つ。FOMC 声明の日は、直前の利下げ確率も取る
4. 発表時刻から30秒間隔で取りに行き、取れた指標から通知する。最長45分
5. 最後に BTC 価格の空欄を埋める

### 拾える時刻（夏時間と冬時間）

毎時の監視は日本時間の毎時23分に動く。米東部と日本の時差は13時間か14時間でちょうど1時間単位なので、米東部でも毎時23分になる。どの発表にも、その前の23分の回が必ずある。

| 発表（米東部） | 待ち受けを始める回（米東部） | 冬時間（EST）の日本時間 | 夏時間（EDT）の日本時間 | 待つ時間 |
|---|---|---|---|---|
| 8:30（CPI・雇用統計・新規失業保険申請・コアPCE） | 8:23 | 22:23 | 21:23 | 約7分 |
| 10:00（今は対象指標なし） | 9:23 | 23:23 | 22:23 | 約37分 |
| 14:00（FOMC声明・議事録） | 13:23 | 翌 3:23 | 翌 2:23 | 約37分 |

- テストでは、冬（例：2026年12月10日）と夏（例：2027年6月10日）の両方で、上の3つの時刻の発表が「待ち受けの対象」になり、1つ前の回（例：7:23）では対象にならないことを確かめる。10:00 は今は対象指標がないので、テスト用の発表を作って確かめる
- 実行時間は最長で、待ち60分 ＋ 取得45分 ＋ いつもの確認で、約110分。**ワークフローの timeout-minutes は、毎時の監視を120分**にする。朝のまとめと手動の月次は20分
- 45分たっても取れなかった指標や、発表がなかった指標は、エラー通知（1回目と復旧時のみ）にし、次の回の予備確認に任せる

### 同時実行と取り消し

- `concurrency` は今の1グループのまま。毎時どうしも、朝のまとめも、1つずつ順に流れる
- 待ち受けで長く動くのは、日本時間でおよそ 20:23〜翌4:45（夏時間は 20:23 の回が 10:00 の発表なしなら短く終わる。下の表）。朝のまとめ（7:47）とは重ならないので、朝のまとめが順番待ちになり取り消されることは普段は起きない
- 万一取り消されても、予備の定時実行が後で送る（朝のまとめは同じ日に送っていれば何もしないので、二重にはならない）
- テストで、冬時間と夏時間の両方について、待ち受けを含む毎時の回が動きうる最長の時間帯（起動から、待ち＋取得45分＋いつもの確認の余裕まで）を日本時間に直し、朝のまとめの起動（7:47）と実行時間（最長20分）に重ならないことを確かめる

|---|---|---|
| 8:30 | 22:23〜23:25 ごろ | 21:23〜22:25 ごろ |
| 10:00 | 23:23〜翌0:55 ごろ | 22:23〜23:55 ごろ |
| 14:00 | 翌3:23〜4:55 ごろ | 翌2:23〜3:55 ごろ |

## 4. 指標ごとの取得と判定

### 実績の取得先

| 指標 | 待ち受けでの主な取得先 | 代わり | 毎時の予備確認 |
|---|---|---|---|
| CPI（4つの数字） | BLS（季節調整あり CUSR0000SA0・CUSR0000SA0L1E、なし CUUR0000SA0・CUUR0000SA0L1E） | FRED（同じ4系列） | FRED |
| 雇用統計（NFP・失業率） | BLS（CES0000000001、LNS14000000） | FRED（PAYEMS、UNRATE） | FRED |
| 新規失業保険申請 | SoSoValue の実績（千件） | FRED（ICSA） | FRED |
| コアPCE | SoSoValue の実績（"0.3%"） | FRED（PCEPILFE から前月比を計算） | FRED |
| FOMC声明 | federalreserve.gov（今の取得処理） | － | 今の確認 |

- 待ち受けは毎回、主な取得先を見て、新しい値がなければ FRED も見る。先に新しい値が出た方を使い、出所を記録する
- **発表時刻から実績が取れるまでの秒数**を、指標・出所・発表日とともに `logs/release_latency.jsonl` に1行ずつ書く

### 予想値

- SoSoValue：config.py に固定した名前で `/macro/events/{event}/history?limit=3` を呼び、実績が `""` の行を次回分とする。行が1件もなければ名前の誤りとしてエラー。行はあるが次回分がないときは、エラーにせず ForexFactory だけを使う
- ForexFactory：週次カレンダーの `country=USD` で、config.py の名前と米東部の日付が合う行を使う
- 取る時刻：朝のまとめで1回、待ち受けの直前に1回。state.json に控え、毎時の予備確認は控えを使う
- 単位をそろえる：
  - SoSoValue の CPI 系とコアPCE は `"0.3%"`、`"0%"`、`"-0.4%"` から % の数値にする
  - SoSoValue の NFP と申請件数は千単位の数字で、`"63"` は6.3万
  - ForexFactory は `"65K"`、`"194K"`、`"0.2%"`、`"4.2%"`、`"-23K"` を同じ単位にする
  - 空欄、`"-"`、数字にならない値は「予想なし」として扱い、エラーにはしない

### 判定（rules.py に追加）

- 実績と、2つの予想の低い方・高い方を比べる。範囲は、それぞれの「同じとみなす幅」を広げたもの（CPI・コアPCE・失業率は小数1桁で一致、NFP は±2.5万人、申請件数は±5,000件）。範囲内なら一致、上なら上振れ、下なら下振れ
- 向きは config.py に置く。上振れが弱気なのは CPI・NFP・コアPCE、強気なのは失業率・申請件数
- 予想が1つならその1つと比べる。どちらもなければ、前回値との比較で判定し「予想値なし」と出す（今と同じ）
- CPI はコア前月比で判定する。コア前年比が逆の結果なら「前年比は逆方向」と添える。総合の2つは並べるだけ
- 前年比は季節調整なし、前月比は季節調整ありの系列で計算し、小数1桁に丸めてから比べる（今の計算を使う）。基準月が欠測なら「—（基準月のデータなし）」とし、判定には使わない
- 雇用統計は NFP で判定し、失業率と合わせて1通にする。失業率が逆の結果なら「失業率は逆方向」と添える。Phase A では失業率が別の通知だったが、設計書の見本に合わせて1通にまとめる
- 通知の形は設計書の見本どおり。予想は範囲で出し（例：`予想 6.3万〜6.5万人`）、予想値の出所を書く

### FOMC

- 期待金利：各レンジの中央値に確率を掛けて足す
- 利下げ確率：今の誘導目標より下のレンジの確率の合計。利上げ確率は上のレンジの合計
- 現在の誘導目標：FRED の DFEDTARU・DFEDTARL
- 3会合先までの織り込み幅：3回先の会合の期待金利と、今の誘導目標の中央との差
- 朝のまとめ：次回会合の利下げ確率と前日比、3会合先までの織り込み幅と前日比。決めてほしいことの1が推奨どおりなら、利上げ確率も出す
- 即時通知：毎時、前回通知した値と比べる。初回は記録だけする。次回会合が切り替わった（会合が終わった）ときは、基準を新しい会合に移すだけで通知しない
- 声明の判定：決定後の誘導目標の中央から会合前の期待金利を引き、+10bp を超えたら弱気、−10bp 未満なら強気、その間なら中立
  - 会合前の期待金利は、会合当日（日本時間）の朝のまとめで控える
  - 当日の待ち受け（米東部 13:23 の回）で取れたら、より直前の値で上書きする（設計書からの小さな変更）
  - 控えがなければ「会合前の織り込みなし」として、今の Phase A と同じ表示にする

### 朝のまとめの追加

- 「今日・明日の予定」：日本時間の今日・明日に発表される対象指標を出す。時刻は日本時間で、予想値は取れたものだけ載せ、なければ「予想 未発表」と書く。FOMC声明・議事録も載せる
- 「金利見通し」：上記のとおり
- 稼働状況：`（SoSoValue 今月の残り 9,876回）` を付ける。上限の2割を切ったら ⚠️ を付けて警告する
- 残り回数は、SoSoValue を呼ぶたびに応答ヘッダーから state.json に記録する（ETF の取得も含める）

## 5. 二重通知の防止

- 経済指標の state に、通知した発表日（`release`）を加える。待ち受けは、通知したらすぐ `release` と対象期間を保存する
- 毎時の予備確認（FRED）は、FRED に新しい期間が出ていても、その発表日の分を通知済みなら記録だけして通知しない
- 同じ回の中では、予備確認は待ち受けの対象になった指標を見ない（待ち受けに任せる）
- 毎時どうしは順番に流れ、実行開始時に最新の main を読むので、前の回が通知した記録が見える
- 取れなかった発表は、次の回の予備確認が FRED で拾う。待ち受けが45分で打ち切った指標は、次の回では「時刻から45分以内」を過ぎているので待ち受けの対象にならず、予備確認で1回だけ通知される

## 6. Phase C

### 通知の記録（`logs/alerts.jsonl`、1通知1行）

- Runtime の送信に、記録用の情報（指標、種類、実績、比べた相手、判定）を渡せるようにする。送信に成功したときだけ書き、dry-run では書かない
- 種類：`immediate`（即時通知）、`daily_flow`、`morning`、`monthly`、`error`、`recovery`
- すべての通知を記録し、当たり率の集計には即時通知と日次フローだけを使う
- 項目：`id`、`ts`（UTC）、`indicator`、`kind`、`actual`、`compared`、`verdict`、`btc_price`、`btc_price_1h`、`btc_price_24h`、`btc_price_72h`。価格は最初は `null`
- 価格の決め方：その時刻を含む OKX の1時間足の終値で、確定した足だけを使う。通知時点も同じ方法で埋めるので、差は1時間ちょうどの値動きになる
- 毎時の監視の最後に、時刻が来た空欄を埋める。取れなければ空欄のまま次の実行で再試行する。必要な時間帯をまとめて取るので、1回の実行で OKX へ1〜2回

### 月次レポート（`reports/YYYY-MM.md` と Discord）

- 1日（日本時間）の朝のまとめのあとに、前月分を送る。state.json の `monthly.last_month` で、同じ月を2回送らない。送れなかったら次の起動か手動の `--mode monthly` で送り直す
- 指標ごとの通知件数
- 当たり率（24時間後・72時間後）：強気のあとに上がり、弱気のあとに下がった割合。中立と価格がない行は除き、何件で計算したかも出す
- 動きの大きさ：通知後の値動き幅の平均を、その月の全時間帯の平均（OKX の1時間足から計算）で割った倍率
- 見直し候補：判定と逆に動くことが多い指標（当たり率50%未満、かつ件数が一定以上）
- Discord には要約を送り、全文は reports/ のファイルに置く
- 月末近くの通知は、1日の時点で72時間後が出ていない。件数を「集計待ち」として明記する

### 過去分の復元（`scripts/reconstruct_history.py`）

- `git log` から state.json の各版を古い順に読み、前の版との差から「いつ、どの指標の通知があったか」を出す
- 旧形式（Phase A の 8cb19a9 まで）の決め方：
  - 値が変わったら通知とみなす：経済指標・FOMC・市場・ステーブルコイン・流動性・取引所純流入
  - SEC：新しい `seen_ids` の数（日付が変わると数え直す）
  - 恐怖&強欲：ゾーンが変わったとき
  - Funding Rate：当時の閾値で判定し直す
- 新形式（Phase A 以降、通知の記録を始めるまで）：経済指標・FOMC・日次フローの更新と、`errors` に増えた項目を通知とする。朝のまとめは `summary.last_date` の更新で数える。VIX は上がったときだけ通知とする（下がったときは基準の付け替えで通知なし）
- 時刻はボットのコミット時刻とする（通知から数分の遅れがある）
- 集計：指標ごと・月ごとの件数と、通知後1時間・24時間・72時間の BTC の値動き幅を、全期間の平均と比べる。当時の判定は記録がないので、当たり率は出さない
- 結果は `reports/history-2026-05-24.md` と、復元した通知の一覧 `reports/history-events.csv` に保存する。実装時に1回実行し、結果もコミットに含める

## 8. state.json の移行（schema_version 2 → 3）

追加するだけで、既存の項目は消さない。読み込み時に自動で移行し、移行は本番の初回実行に任せる（ローカルの state.json は書き換えない）。

| 項目 | 初期値 | 中身 |
|---|---|---|
| `cpi`・`nfp`・`unrate`・`icsa`・`core_pce` の `release` | `null` | 通知した発表日。`null` のときは、今までどおり対象期間で新着を判断する |
| `calendar` | `{"fetched": null, "releases": []}` | FRED の発表日程の控え。朝のまとめで更新し、古ければ毎時の監視でも取り直す |
| `forecasts` | `{}` | 指標ごとの次回分の予想（SoSoValue・ForexFactory、取った時刻） |
| `fomc_outlook` | `{"morning": null, "notified": null, "pre_meeting": {}}` | 前日比の基準、通知の基準、会合前の期待金利 |
| `fed_target` | `null` | 誘導目標の上限・下限と日付 |
| `sosovalue` | `{"remaining_month": null, "limit_month": null, "checked_at": null}` | 残り回数 |
| `monthly` | `{"last_month": null}` | 送った月 |

- 通知の記録と発表までの時間は state.json ではなく `logs/` に置く。state.json を小さく保つため
- 最初の実行では、利下げ確率は記録だけで通知しない。予想値の控えは朝のまとめから始まる

## 10. テスト

- 判定（過去の発表データ）
  - 2つの予想が一致した回：CPI 11月10日（コア前月比 0.3%、予想 0.2% と 0.2%、上振れで弱気）、新規失業保険申請 11月12日（20.0万件、予想 19.4万件と 194K、上振れで強気）
  - 予想が割れた回：NFP 11月6日（実績 16.5万人、予想 6.3万人（11月4日時点）と 65K、範囲は 3.8万〜9.0万人、上振れで弱気）
  - 予想と一致した回：コアPCE 10月29日（0.3%、予想 0.3%）
  - 片方だけの回、両方ない回
  - 割れた予想の範囲内に入る回は、実データにないので作った値で確かめる
- 文字列の変換：`"0%"`、`"-0.4%"`、`"63"`、`""`、`"65K"`、`"-23K"`、`"4.2%"`
- SoSoValue：0件はエラー、次回の行なしはエラーにしない、残り回数の記録と2割の警告
- 利下げ確率：配列が短い会合、期待金利、利下げ・利上げ確率、15pt の通知、会合の切り替わり、声明の ±10bp
- 発表待ち受け（時計と sleep を差し替える）
  - 冬時間と夏時間の両方で、8:30・10:00・14:00 の発表を23分の回が対象にし、1つ前の回は対象にしない
  - 発表時刻までの待機、30秒間隔、45分の打ち切り
  - BLS が失敗したら FRED、発表までの秒数の記録
  - 発表がない回はすぐ終わる、遅れて動いた回（時刻から45分以内）は拾う
- 二重防止：待ち受けのあとの次の回の予備確認、打ち切った指標を次の回が1回だけ通知する
- 朝のまとめとの重なり：冬時間・夏時間の両方で、待ち受けで長く動く時間帯が朝のまとめの起動と実行時間に重ならない
- ワークフロー：concurrency が1グループのまま、timeout-minutes が毎時120分・ほか20分
- 記録：追記、送信失敗では書かない、価格の書き足し、取れなかった行の再試行
- 月次：当たり率、中立と価格なしの除外、倍率、同じ月を2回送らない、1日の朝のまとめで送る
- 復元：作った履歴（旧形式と新形式）での数え方
- 移行：v2 から v3、すでに v3 なら何もしない
- BLS：エラー本文のキーがログに出ないこと

## 11. 残るリスクと制約

- BLS のキーが直るまでは、CPI と雇用統計も FRED で取る。FRED は BLS より数分遅いことがある
- SoSoValue の申請件数・コアPCE の実績が、発表から何分で入るかは未確認。待ち受けの記録で分かる
- CPI とコアPCE の予想値が SoSoValue に何日前に載るかは未確認。朝のまとめで「予想 未発表」と出ることがある
- 今の CPI のように前年比の予想がどちらにもない回は、前年比を予想なしで載せる
- 利下げ確率の配列を先頭から対応させるのは、データの形からの推測。今の値（利上げ84.5%）が FedWatch などと合うかは、自分の目で一度確かめてほしい
- 毎時の23分の回が GitHub 側で遅れたり飛ばされたりすると、その発表は待ち受けで拾えず、次の回の予備確認（最大で約1時間後）になる。外部タイマーの毎時の起動が頼り
- 待ち受け中の回は最長約110分続く。その間の次の毎時の起動は順番待ちになり、待ち受けが終わってから動く
- 朝のまとめが順番待ちの間に別の起動が来ると取り消されうる。待ち受けの時間帯とは重ならないので普段は起きず、起きても予備の定時実行が後で送る
