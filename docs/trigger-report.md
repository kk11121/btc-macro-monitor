# 外部タイマー起動への対応 報告

作成日：2026年11月12日

状態：**実装とテストは完了。コミットとプッシュの前で止めている**

## 背景

GitHub の定時実行は間引かれ、実行が数時間遅れていた。直近7日のボットのコミット時刻を見ると、日本時間 7:47 予定の朝のまとめは 10:53〜13:21 に動いていた。そこで、cron-job.org から `workflow_dispatch` で起動する形に変える。

## 結果

- テスト：239件すべて成功（前回から12件増）
- カバレッジ：98%（全体）
- 静的チェック：ruff の指摘は変更前と同じ 27件で、今回の変更による増加はない（下の「注意」を参照）
- ローカルの `state.json` と `history/etf_flows.json`：dry-run の前後でハッシュが同じ。どちらも変更していない

## 変えたこと

### 1. 朝のまとめの二重送信防止（`jobs_morning.py`）

- その日（日本時間）のまとめを送っていれば、何もせずに終わる。日次フローの確認も含めて何もしない（日次フローは毎時の監視でも確認している）
- 送ったかどうかは、既存の `summary.last_date` で判断する。送信に成功したときだけ記録されるので、失敗した日は次の起動で送り直す
- `main.py --force` を付けると、送信済みでも送り直す。`hourly` で付けても無視し、ログに残す

### 2. ワークフロー（`.github/workflows/scheduler.yml`）

- `workflow_dispatch` に `force`（boolean、既定 false）を追加した。API から `"true"` の文字列で送っても効く
- `schedule` は予備として残した。時刻は変えていない
- `actions/checkout` に `ref: main` を足した。理由は後述

### 3. 前年比の基準月が欠測のとき（`jobs_hourly.py`、`rules.py`）

- 基準月が欠測なら「—（基準月のデータなし）」と表示する。先月の前年比でも同じ
- 「欠測」は、取得した範囲の中にその月の行がない場合に限る。取得範囲が足りないだけのときは、これまでどおり「―」と出し、欠測とは書かない
- 対象月そのものがないときも「―」のまま
- 表示例（2026年10月分）：`コア前年比 —（基準月のデータなし）（先月 +2.6%）`

### 4. README

- 外部タイマーからの起動方法を書いた：API のアドレス、ヘッダー、送る内容（朝と毎時）、送り直しのときの内容、トークンの権限（fine-grained の Actions: Read and write）、手元から試す curl、同時に起動されたときの動き
- ジョブの表を「予備の定時実行」に書き換え、`--force` と前年比の表示を追記した

## 頼まれていないが足したこと

`actions/checkout` に `ref: main` を足した。

- 以前は、起動した時点のコミットを取り出していた。順番待ちの実行は、前の実行が保存した `state.json` を読めない
- それでは、朝のまとめが外部タイマーと定時実行でほぼ同時に起動したとき、2回目も「未送信」と判断して二重に送る
- 同じ理由で、毎時の監視が二重に通知し、`state.json` の rebase が衝突する恐れもあった
- 影響：`main` 以外のブランチを指定して手動実行しても、`main` のコードで動く。今は `main` しか使っていないので問題ないと判断した

## 確認したこと

- 本番の `state.json` を使った dry-run（送信も保存もしない）
  - 朝のまとめ：今日の分は送信済み（`last_date` が 2026-11-12）なので、何もせず終わった
  - 朝のまとめを `--force` 付きで実行：まとめの本文が組み立てられた
  - 毎時の監視を `--force` 付きで実行：「無視します」とログに出て、通常どおり動いた
- FRED の実データ：CPI の季節調整なし系列（総合とコア）で 2025年10月が欠測と判定され、最新の 2026年10月分の前年比は「—（基準月のデータなし）」になった
- 追加したテスト
  - 送信済みなら何もしない
  - `force` なら送り直す
  - 同じ日の2回目は送らない
  - 送信に失敗した日は次の起動で送り直せる
  - 既定の日付は日本時間（UTC 22:47 は翌日扱い）
  - `--force` を朝のまとめに渡す
  - `--force` を `hourly` では無視する
  - 前年比：当月の基準月の欠測、先月の基準月の欠測、取得範囲不足の区別
  - `is_missing_month` の単体テスト

## 確認できていないこと

- GitHub Actions 上の実行と、cron-job.org からの実際の起動。ワークフローは YAML として読めることだけ確認した
- `force` を JSON の `true`（文字列ではなく真偽値）で送ったときの扱い。どちらでも効くように比べているが、実地では試していない
- dispatch API の成功時の応答コード。最新の文書は 200（実行の ID 付き）だけを載せている。以前の 204 もあり得るので、README には「2xx」と書いた

## 知っておいてほしいこと

- 2026年10月分の CPI は、本番が 11/10 にもう通知済みで、そのときは前年比が「―」だった。新しい表示が初めて出るのは、12月中旬の11月分 CPI の「先月」の欄
- 表示の記号は指定どおり「—」（全角ダッシュ U+2014）にした。ほかの「値なし」は従来の「―」（U+2015）のまま
- 同時起動の制限：GitHub の `concurrency` では、順番待ちは1件だけ。さらに起動されると古い待ちは取り消される。朝のまとめが取り消されても、その日に未送信なら後から動く予備の定時実行が送る
- 予備の定時実行が16時間以上遅れて日本時間の翌日に入ると、翌日のまとめを早朝より前に送り、7:47 の外部起動は送信済みとして何もしない。今の遅れ（最大5時間ほど）なら起きないので、対策は入れていない
- ruff：新しく入れ直した ruff（新しい版）は既定の規則が増えていて、変更前のコードにも27件の指摘が出る。今回の変更では増やしていない。既存分の整理は別の作業にした

## お願いしたいこと

1. cron-job.org の設定：README の「外部タイマーからの起動」のとおり、朝と毎時の2つの予定を作る。タイムゾーンは Asia/Tokyo
2. fine-grained トークンを作る：対象はこのリポジトリだけ、権限は Actions: Read and write、期限付き。トークンは cron-job.org にだけ入れる
3. コミットとプッシュに進んでよいか決める。プッシュすると、次の実行から新しいワークフローと二重送信防止が効く
